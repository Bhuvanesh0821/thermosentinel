# Deploying ThermoSentinel

Production layout: **Vercel** (React frontend) → **Render** (FastAPI, Docker, Singapore) →
**Neon** (PostgreSQL + PostGIS, Singapore). Background ingestion runs inside the API process;
**GitHub Actions** runs CI and keeps the free Render instance awake. All secrets live in the
Render dashboard - never in the repository or the browser bundle.

| Piece | Service | Plan | Config in repo |
|-------|---------|------|----------------|
| Frontend | Vercel | Hobby (free) | `frontend/vercel.json`, `frontend/.env.production` |
| Backend | Render web service (Docker) | Free (512 MB, sleeps after 15 min idle) | `render.yaml`, `docker/backend.Dockerfile` |
| Database | Neon | Free | `database/migrations/` (applied automatically at start-up) |
| CI + keep-alive | GitHub Actions | Free (public repo) | `.github/workflows/` |

## 0. Prerequisites

* Accounts: GitHub, Render, Vercel, Neon (project in **AWS ap-southeast-1 / Singapore**).
* The Neon **pooled** connection string (Neon → Connect → "Pooled connection"), ending in
  `?sslmode=require`. Keep it out of chat, issues and commits.
* Optional: a NASA FIRMS MAP_KEY (https://firms.modaps.eosdis.nasa.gov/api/map_key/). Without it
  the keyless public 7-day feed is used.

## 1. Push the code to GitHub

```bash
git remote add origin https://github.com/<you>/thermosentinel.git
git push -u origin main
```

`.env` is git-ignored; verify with `git status` that it never appears. The only env files in the
repository are `.env.example` (no values), `frontend/.env.production` (the public API URL) and
`frontend/.env.same-origin` (local preview mode).

## 2. Backend on Render

1. Render dashboard → **New → Blueprint** → connect the GitHub repository. Render reads
   `render.yaml` and proposes the `thermosentinel-api` web service (Docker, Singapore, free).
2. Fill the values marked *sync: false*:

   | Variable | Value |
   |----------|-------|
   | `DATABASE_URL` | Neon pooled connection string (secret) |
   | `FRONTEND_URL` | Vercel URL, e.g. `https://thermosentinel.vercel.app` (fill after step 3, or use the expected URL now) |
   | `BACKEND_URL` | This service's URL, e.g. `https://thermosentinel-api.onrender.com` |
   | `NASA_FIRMS_MAP_KEY` | optional (secret) |
   | `NOTIFY_WEBHOOK_URL`, `SMTP_*`, `NOTIFY_EMAIL_TO` | optional alert delivery (secrets) |

   `ADMIN_API_TOKEN` is generated by Render automatically. `APP_ENV=production` is preset.
3. **Apply**. The first build installs the pinned Python 3.14 wheels (a few minutes). On start
   the API validates its configuration, applies migrations to Neon, syncs the India boundary and
   starts the scheduler; the first FIRMS ingestion runs ~20 s later.
4. Check `https://<service>.onrender.com/api/health` → `"status": "ok"`, database `connected`,
   `"environment": "production"`, `"data_mode": "live"`.

If the service name is taken, Render adds a suffix to the URL: use the real URL everywhere below.

**Start-up refuses unsafe configuration.** If the log shows `Refusing to start in production`,
it names the missing piece (e.g. `FRONTEND_URL is not set`). Fix it under Environment and
redeploy.

## 3. Frontend on Vercel

1. Make sure `frontend/.env.production` contains the real Render URL:
   `VITE_API_BASE_URL=https://<service>.onrender.com` (commit and push if you change it).
2. Vercel → **Add New → Project** → import the repository → **Root Directory: `frontend`**.
   Framework: Vite (detected; `vercel.json` sets install/build/output). No secrets are needed.
3. Deploy, then note the production URL (e.g. `https://thermosentinel.vercel.app`).
4. Back in Render, set `FRONTEND_URL` to that exact URL (no trailing slash) → the service
   redeploys. The API now accepts REST, WebSocket and SSE connections from that origin only.

A production build without `VITE_API_BASE_URL` (or with a non-HTTPS URL) fails on purpose.

## 4. Keep-alive and CI (GitHub Actions)

* Repository → Settings → Secrets and variables → Actions → **Variables** → New variable:
  `BACKEND_URL` = `https://<service>.onrender.com`. The *Keep API awake* workflow then pings
  `/api/health` every 10 minutes so ingestion and live alerts keep running on the free plan.
  (GitHub may delay scheduled runs; a paid Render instance removes the need entirely.)
* The *CI* workflow runs the full test suite (with a PostGIS service container) and the
  production frontend build on every push.

## 5. Verify the deployment end to end

```bash
API=https://<service>.onrender.com
curl -s $API/api/health            # environment=production, database connected, data_mode=live
curl -s $API/api/system/health     # every component + recent failures per category
curl -s "$API/api/alerts?limit=1"  # real alerts
```

Then open the Vercel URL: the top bar shows **Live** (WebSocket), the map loads with real
detections, the notification bell lists real alerts, and Settings → System health shows every
component. `$API/api/docs` serves the OpenAPI documentation.

To trigger a pipeline run manually in production (operators only):

```bash
curl -X POST -H "X-Admin-Token: <value from Render → Environment>" "$API/api/pipeline/run"
```

## 6. Operations

* **Logs**: Render → Logs (structured JSON; secrets are never logged).
* **Health**: `/api/health` (liveness, used by Render), `/api/system/health` (components and
  failures in the last 24 h: ingestion, external sources, database, API, alerts,
  notifications, real-time).
* **Redeploys** are zero-config: push to `main` → Render and Vercel rebuild. Streaming
  connections get 10 s to close; browsers reconnect and refetch automatically.
* **Database**: Neon free tier (0.5 GB). `OBSERVATION_RETENTION_DAYS` (120) keeps storage in
  bounds. Migrations are forward-only and applied at start-up.
* **Scaling**: raise the Render plan for always-on and more memory. More than one instance is
  safe for ingestion (database job lease), but in-process real-time events are per instance.

## 7. Local container run (optional)

```bash
docker compose -f docker/docker-compose.yml up --build   # web on http://localhost:8080
```

The web container serves the build behind nginx and proxies `/api` and `/ws` to the API
container (`VITE_API_SAME_ORIGIN=true`); the API reads `../.env`.
